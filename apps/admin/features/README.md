# 后台业务能力模块规划

> 依据：[后台需求](../../../docs/admin/需求.md)、[原型](../../../docs/admin/原型.md)、[接口能力清单](../../../docs/admin/接口清单.md)与[共通规则](../../../docs/common/业务规则与跨端流程.md)。名称和边界是候选，**不是已有源码、HTTP 契约或固定包结构**。

按业务能力承接状态、交互与未来数据访问；模块可根据正式契约拆并，不让页面/应用壳直接调用假定后端字段。原始 PRD §5.3 的 16 组需求均有对应归属：

| 候选能力 | 需求优先级 | 边界提示 |
| --- | --- | --- |
| auth / access | 角色/菜单/数据权限 P0；菜单管理 P1 | 登录原型有账号密码；菜单/按钮展示不替代服务端逐请求鉴权与数据范围校验。 |
| dashboard | 今日订单、GMV、新用户、待审核/待办 P0；趋势图 P1 | 汇总仅为服务端指标视图，不重算审核和资金状态。 |
| onboarding-review / qualification-review | 入驻及实名/健康证/美容师证审核 P0 | 审核意见、状态、证件有效期与过期停接单由服务端保障，记录审计。 |
| payout-review / refund-review | 提现与退款/售后审核 P0 | 审核中心与财务/订单入口复用同一动作能力，不能多套规则；打款/退款结果需服务端核实。 |
| consumer-management | 列表、详情、封禁 P1 | 按角色及数据范围展示敏感信息。 |
| provider-management | 美容师列表/详情 P0；奖惩/禁用、到期提醒 P1 | 详情聚合资质、项目、排班、订单、收益、评价；独立抽成变更由抽成能力承接。 |
| catalog-management | 项目分类、价格、时长、上下架 P0 | 服务时长影响未来排班占用；不在后台页面覆盖已创建订单。 |
| service-order | 服务订单筛选/导出/详情、退款 P0；改派 P1 | 只按服务端状态允许动作；改派并发/占用及退款抽成冲正待契约。 |
| schedule-dispatch | 时间池、冲突标记 P1 | 半小时 + 前后缓冲 + 项目时长；后台只展示冲突，最终占用校验服务端负责。 |
| commission | 默认/条件模板、独立抽成 P0 | 订单创建时保存抽成快照，历史订单不随模板修改；原型“专属模板”优先级细则待确认。 |
| finance | 支付流水、结算单、提现/退款记录 P0；对账 P1 | 平台统一收款，默认 T+7 可配置；记录查询与提现审核/打款动作解耦。 |
| marketing / content | 优惠券、Banner P1；活动、发现页、评论审核 P2 | 不将优惠分摊规则藏在运营页面；内容发布与评论审核按原文优先级。 |
| review / complaints | 评价审核及投诉/申诉 P1 | 评论审核 P2 与评价审核 P1 各保留原始范围。 |
| mall | 商品/库存、独立商城订单、发货物流、售后 P1 | 商城订单与服务订单资金/状态隔离，不影响美容师接单资格与等级。 |
| notifications | 推送、短信模板、站内信记录 P1 | 渠道接入与触达结果待契约，不能凭前端提交宣称已发送。 |
| analytics | 经营/订单/用户/美容师统计 P1；区域热力 P2 | 指标口径、城市维度及权限由正式契约统一。 |
| system-rules / audit | 结算周期/提现/优惠分摊规则 P0；操作日志、城市/距离、协议/隐私 P1 | 规则配置与具体服务端计算分离；日志查询 P1 不意味着 P0 审核/财务动作可无留痕。 |

模块之间只共享清晰的数据访问边界和标识，不在 shared 中实现抽成/结算或将商城订单并入 service-order。上门费参与抽成、抽成快照、退款冲正、余额 > 1 元、资质过期自动停接单等实际判定仍由服务端权威执行。后续实现处写约束注释及测试，见[骨架设计](../ARCHITECTURE.md)。
