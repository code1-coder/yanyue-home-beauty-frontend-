> 状态：待评审，**不是已初始化的 uni-app 工程**。仅建立目录和 Markdown，不创建页面、业务逻辑、接口桩、模拟数据或配置文件。

> 需求依据：[原始 PRD §4、§5.1、§6、§8.1、§9、§11](../../docs/服务产品需求文档（PRD）.md)；页面依据：[原始原型 §二、§五、§六、§七](../../docs/原型整体结构.md)。拆分索引：[需求](../../docs/consumer/需求.md)、[原型](../../docs/consumer/原型.md)、[接口能力](../../docs/consumer/接口清单.md)、[共通规则](../../docs/common/业务规则与跨端流程.md)。业务需求和原型差异以两份原始文档为准；技术方向见[技术选型与仓库结构](../../docs/技术选型与仓库结构.md)，不替代原始产品功能、支付渠道与优先级；其余记录待确认项。

## 目标与边界

- 当前优先规划 HBuilderX + uni-app Vue 3 + uview-plus 的**独立消费者微信小程序工程**，不建立 Android/iOS 工程；这不取消原始 PRD 的兼容要求。框架与组件的兼容组合待工程验证。
- 保持原型首页 / 发现 / 我的三个 TabBar 入口，以薄页面、业务模块、端内共享、平台适配分层；原型路径仅是建议，尚无实际路由注册。
- 只负责浏览、预约、支付入口、订单/售后展示、评价和个人中心；不混入美容师接单/排班编辑、抽成结算、提现审核或后台管理。
- 页面消费待设计接口能力，不猜测 HTTP 路径和字段；可约性、金额、支付结果、退款和订单状态以服务端权威结果为准。

这四层是**未来源码放置约定**，不是已存在的源码或已确认的框架 API。获准编码后，pages 放原型路由对应的薄页面入口，features 放按业务切分的交互、状态和数据访问，shared 放无业务归属的端内通用能力，platform 收拢微信小程序登录、定位、支付与权限适配。应用入口、pages.json、manifest.json、uview-plus 引入及静态资源目录待技术验证后再建立，不创建空配置。

依赖方向建议：pages → features → shared / platform；业务模块不直接依赖其他模块的页面或内部状态。跨模块使用明确的公开边界、服务端契约与稳定标识，避免多页重复计算订单金额或复制支付结论。三端不能仅因共用 uni-app 就共享未经确认的运行时业务代码，跨端状态最终由服务端保障。

## 页面与阶段

完整 28 个原型页面入口见 [pages/README.md](pages/README.md)。第一阶段以登录、首页、项目、美容师、预约、支付、订单、评价、我的闭环规划，地址管理是预约需要的 P0 能力。发现为 PRD P2、原型第二阶段；消息在 PRD 是 P0、在原型排第二阶段：**优先级不等于交付阶段**，首期 TabBar 展示方式及消息交付范围须产品确认，不能自行改写优先级。优惠券 P1、安全中心 P2 等按确认后的阶段安排。

原型路径如 /pages/order/booking 是页面标识草案，不是已存在的 uni-app 文件路径。以后如采用分包，应保留页面语义并验证 TabBar 主包、导航兼容性和目标平台要求；本仓已采用三端独立目录，不额外建立消费者/服务者混合包。

## 接口边界和关键交互

[接口能力清单](../../docs/consumer/接口清单.md)仅盘点能力，未确认 URL、方法、字段、错误码、鉴权、分页、上传、回调和版本。未来以各 features 模块的对外数据访问边界承接正式协议，不让页面直接假定后端字段，也不伪造 API。

1. 首页/项目/美容师 → 预约：读取候选时段、地址及上门费/金额试算，再提交服务端创建服务订单。半小时排班、项目服务时长及前后缓冲共同影响占用；并发冲突由服务端最终处理。
2. 确认订单 → 支付 → 结果：取服务端订单和支付状态。重复提交、回跳、主动查询/轮询及幂等口径待正式契约确认。
3. 订单列表/详情 → 取消/售后/评价：只展示服务端状态和允许的操作；退款金额、抽成冲正与结算不由消费者端判定。
4. 定位/地址 → 美容师/预约：距离用于展示和超区提示，**超半径仍可下单**且美容师可拒单，客户端不可强制禁用。
