# 数据库表设计草案

> 本文是上门美容服务后端的数据库设计草案，字段和索引用于接口与模块设计评审，不是最终 DDL。最终建表前需要根据现有 RuoYi-Vue-Pro 版本、MySQL 方言、统一字段规范和产品确认结果调整。

## 1. 设计原则

### 1.1 表命名

- 表名前缀统一使用 `beauty_`
- 使用小写字母和下划线
- 业务表使用逻辑删除：`deleted`
- 通用字段沿用项目约定：
  - `id`：主键，BIGINT
  - `creator`：创建人
  - `create_time`：创建时间
  - `updater`：更新人
  - `update_time`：更新时间
  - `deleted`：删除标记
  - `tenant_id`：租户编号（如果当前模块启用多租户）

### 1.2 金额与时间

- 金额统一使用 `BIGINT`，单位为分，例如 `price_fen`
- 比例使用 `DECIMAL(5, 2)`，例如 `10.00` 表示 10%
- 时间戳使用 `DATETIME`，日期使用 `DATE`
- 不直接使用浮点类型存储金额

### 1.3 状态字段

- 状态值由 Java 枚举统一维护
- 数据库保存整数或约定字符串，推荐使用整数枚举
- 不直接依赖展示文案判断状态

### 1.4 快照与历史

- 订单中的项目名称、价格、时长、上门费、优惠、抽成和结算周期必须保存快照
- 平台项目、服务者项目和抽成模板后续修改不影响历史订单
- 需要追溯价格变化时，使用独立的价格历史表

### 3.3 `beauty_provider_project` 服务者项目关联

该表解决“不同服务者可接项目集合不同、同一项目价格不同”的核心需求。

| 字段 | 类型 | 说明 |
|-----|------|------|
| `id` | BIGINT | 关联编号 |
| `provider_id` | BIGINT | 服务者编号 |
| `project_id` | BIGINT | 平台项目编号 |
| `enabled` | TINYINT | 服务者是否启用 |
| `provider_price` | BIGINT | 服务者价格，分，首期建议必填 |
| `provider_note` | VARCHAR(500) | 服务者个性化说明 |
| `sort` | INT | 服务者侧排序 |
| `enabled_from` | DATETIME | 生效时间 |
| `disabled_at` | DATETIME | 停用时间 |
| `status` | TINYINT | 正常/平台禁用 |
| 通用字段 | - | 创建、更新、逻辑删除、租户 |

**约束与索引**：
- `uk_provider_project (provider_id, project_id, deleted)`
- `idx_project_enabled (project_id, enabled, status, deleted)`
- `idx_provider_enabled (provider_id, enabled, status, deleted)`

**业务约束**：
- 平台项目下架后，关联记录不删除，但消费者不可下单
- 服务者停用关联后，新的报价和预约不可使用
- 历史订单通过快照展示，不回读当前价格
- 服务者不能修改平台项目名称、标准时长和禁忌

### 3.4 `beauty_provider_project_price` 服务者项目价格历史（可选）

首期如果只需要当前价格和订单快照，可暂不建表；如果需要定时生效、价格审计或价格回滚，启用此表。

## 10. 数据安全与归档

### 10.1 敏感字段

- 身份证号、证件号、银行卡号等字段加密存储
- 手机号和姓名在非必要场景脱敏
- 资质文件使用私有对象存储或受控下载接口
- 日志中不记录完整身份证号、银行卡号和支付密钥

### 10.2 数据归档

- 服务订单、订单日志、财务流水属于长期审计数据，不做物理删除
- 超过业务保留期限后归档到历史表或冷存储
- 归档前确保管理后台仍可按订单号查询摘要
- 订单快照字段不得依赖被归档的当前项目记录

### 10.3 外键策略

- 业务上维护逻辑外键，不强制数据库物理外键
- 删除平台项目、服务者和会员前检查关联数据
- 已有订单的服务者和项目只允许禁用，不允许物理删除
